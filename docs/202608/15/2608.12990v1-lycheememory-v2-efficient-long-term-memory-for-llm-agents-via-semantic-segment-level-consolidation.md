## 摘要
长时程LLM智能体必须保留过去交互中的信息以支持未来任务。现有记忆系统通常采用急切整合（eager consolidation），在每次交互后调用LLM来提取、摘要或更新记忆。这种设计使得随着对话增长，记忆构建的成本不断增加。粗粒度摘要可以降低构建成本，但存在丢弃细粒度上下文证据的风险，而更大的检索上下文或多跳LLM推理则将开销转移到查询阶段。我们提出LycheeMemory V2，一种高效长期记忆框架，用语义片段级整合取代轮次级整合。LycheeMemory不是整合每次交互，而是将多次交流批量划分为片段，并将每个已定稿的片段编码为上下文无关的类型化记忆记录。与固定窗口批处理相比，片段级批处理降低了LLM编码频率，而语义边界检测有助于保留连贯的事件级和时间级证据。生成的记录通过轻量级结构化索引组织，用于查询规划的检索。使用GPT-4.1-Mini的实验表明，LycheeMemory达到了最先进的性能，在LoCoMo上达到89.22%，在LongMemEval-S上达到92.20%。与A-Mem相比，在LoCoMo上构建token减少了86.0%，在LongMemEval-S上减少了75.9%，且不增加查询时token使用量。更广泛地，我们的结果表明，长期智能体记忆的精度-成本权衡不仅取决于保留什么信息，还取决于整合的粒度。

## Abstract
Long-horizon LLM agents must preserve information from past interactions to support future tasks. Existing memory systems typically rely on eager consolidation, invoking LLMs after each interaction to extract, summarize, or update memories. This design makes memory construction increasingly costly as conversations grow. Coarse summarization can reduce construction cost but risks discarding fine-grained contextual evidence, whereas larger retrieval contexts or multi-hop LLM reasoning shift the overhead to query time. We present LycheeMemory V2, an efficient long-term memory framework that replaces turn-level consolidation with semantic segment-level consolidation. Instead of consolidating every interaction, LycheeMemory batches multiple exchanges into segments and encodes each finalized segment into context-independent typed memory records. Segment-level batching lowers LLM encoding frequency, while semantic boundary detection helps preserve coherent event-level and temporal evidence compared with fixed-window batching. The resulting records are organized with lightweight structured indexes for query-planned evidence retrieval. Experiments using GPT-4.1-Mini show that LycheeMemory achieves state-of-the-art performance, reaching 89.22% on LoCoMo and 92.20% on LongMemEval-S. Compared with A-Mem, it reduces construction tokens by 86.0% on LoCoMo and 75.9% on LongMemEval-S without increasing query-time token usage. More broadly, our results suggest that the accuracy--cost trade-off of long-term agent memory depends not only on what information is retained, but also on the granularity at which it is consolidated.

## 1. 论文的核心问题与整体含义

### 研究动机与背景
- **长期记忆的必要性**：LLM 智能体（如个人助手、客服、辅导系统）需要在跨会话、长时程交互中保留用户偏好、历史事件、演变的事实和约束等。然而，LLM 无法在有限的上下文窗口中无界保存全部交互历史，因此外部记忆模块成为关键组件。
- **现有方案的成本困境**：
  - **急切整合（Eager Consolidation）**：现有主流系统（如 Mem0、A-Mem、MemoryOS）在每一轮或每次短交互后调用 LLM 进行提取、摘要或更新，构建成本随对话增长快速累积。
  - **粗粒度摘要**：降低构建成本但容易丢失细粒度语境证据（实体、时间表达式、指代关系、细节上下文）。
  - **查询端补偿**：通过扩大检索上下文或多跳 LLM 推理提升召回，但把开销转移到了查询时间。
- **核心挑战**：不是"如何存储更多历史"，而是**如何在合适的粒度上保留充分证据，同时控制构建和检索成本**。
- **论文提出的核心论点**：长期记忆的精度-成本权衡不仅取决于**保留什么信息**，还取决于**以何种粒度（granularity）进行整合**。

## 2. 论文提出的方法论

### 核心思想
LycheeMemory V2 用**语义片段级整合（Semantic Segment-Level Consolidation）**取代逐轮级整合：

- 将多次交互批量划分为语义连贯的片段（segment），仅在片段定稿后调用一次 LLM 编码，而非每轮都调用。
- 片段级批处理降低 LLM 编码频率；语义边界检测比固定窗口更好地保留连贯的事件级和时间级证据。
- 每个片段被编码为**上下文无关的类型化记忆记录**（typed memory records），配合轻量结构化索引支持查询规划式检索。

### 关键技术细节

#### (1) 在线语义分割（Online Semantic Segmentation）
- 目标：确定何时一个对话片段"足够完整"可以进行整合。
- 对每个新交换 $x_t$ 计算**语义惊喜分数**：
  $$s_t = 1 - \max\{ \text{sim}(e_t, c_k), \text{sim}(e_t, h_k) \}$$
  其中 $e_t$ 为交换 embedding，$c_k$ 为片段质心，$h_k$ 为最近交换 embedding。
- 计算**内聚度下降** $d_t$：将 $x_t$ 加入当前片段前后，片段整体内聚度的下降量。
- 最终边界分数综合语义惊喜、内聚度下降、token 压力和轮数压力：
  $$p_t = \sigma(b + w_s \phi(s_t) + w_c d_t + w_l L_t + w_n N_t)$$
- 当 $p_t$ 超过阈值 $\delta$（默认0.50）或达到硬 token 上限（900 tokens）时，定稿当前片段。
- 边界决策完全基于 embedding 计算，中间过程不调用 LLM。

#### (2) 片段级记忆编码（Segment-Level Memory Encoding）
- 对定稿片段 $S_k$，编码器接收片段文本 + 紧凑参考上下文 $\rho_k$，输出记忆记录集 $R_k$ 和更新后的消歧状态 $d_k$。
- 单次编码完成三项操作：**提取原子信息单元、解析指代和省略指称、用会话时间戳标准化相对时间表达**。
- 每个记录的结构：
  $$r_i = \langle id_i, \tau_i, \text{text}_i, E_i, K_i, T_i, src_i \rangle$$
  包含记录 ID、记忆类型（事实/偏好/事件/约束/流程/失败模式/工具能力）、自包含自然语言陈述、实体集、话题标签集、归一化时间范围和源对话溯源。
- 跨片段连续性：通过轻量**消歧状态** $d_k$ 和最近记录摘要（有固定预算截断）构成下一片段的参考上下文，保持实体别名和指代关系的一致性，且提示大小不随历史增长。

#### (3) 结构化证据组织（Structured Evidence Organization）
- 记录插入向量存储 + 结构化存储，无需额外 LLM 调用。
- 维护五类证据节点：
  - **实体节点**（entity nodes）
  - **话题节点**（topic nodes）
  - **实体-话题节点**（entity-topic nodes）
  - **时间节点**（temporal nodes，日/月粒度）
  - **事件框架节点**（event-frame nodes，按语义片段分组记录并保留溯源）
- 组织阶段只涉及 embedding 和记账操作，构建侧 LLM 成本仍主要由片段编码主导。

#### (4) 查询规划式多路检索（Plan-Guided Multi-Route Retrieval）
- 一次 LLM 规划调用将查询分解为多个**类型化召回路径**：
  $$\Pi(q, H_q) = \langle y, \{R_1,\ldots,R_m\} \rangle$$
  其中 $y$ 为问题类型，每条路径 $R_j$ 包含路径目标、搜索查询、结构约束和可选时间约束。
- 每条路径并行执行四个召回通道：**直接记录召回、证据节点召回、时间召回、原始轮次召回**。
- 路径级候选通过**倒数排名融合（RRF）**合并：
  $$\text{RRF}(d) = \sum_{j=1}^{m} \frac{1}{\kappa + \text{rank}_j(d)}$$
  随后经轻量交叉编码器重排序和多样性感知选择。
- 检索阶段唯一的生成式操作是规划调用；后续召回、扩展、重排、融合、选择均为 embedding 查找、结构化过滤或算术计算，不消耗生成 token。

## 6. 论文的主要结论与发现

1. **性能 SOTA**：GPT-4.1-Mini 下 LoCoMo 达 89.22%（vs. Full Context 84.80%，TiMem 83.77%）；LongMemEval-S 达 92.20%（vs. TiMem 75.80%）。GPT-4o-Mini 下也稳定领先。
2. **构建成本大幅降低**：与 A-Mem 相比，构建 token 在 LoCoMo 上减少 **86.0%**（204.1K vs. 1459.9K），在 LongMemEval-S 上减少 **75.9%**（304.7K vs. 1264.3K）；较 TiMem 分别降低 58.3% 和 50.9%。
3. **查询成本不升反降**：与 A-Mem 相比，LoCoMo 查询 token 降低 27.9%（4.01K vs. 5.56K），LongMemEval-S 降低 42.6%（8.88K vs. 15.46K）。
4. **消融验证**：
   - 急切整合精度 -7.3 pp、成本 +316%；固定窗口精度 -6.8 pp——说明**批处理降低构建成本，语义边界提升精度**。
   - 摘要级记录精度 -8.4 pp（时间推理 -12.8 pp），说明类型化记录优于摘要。
   - 移除查询规划器精度 -5.8 pp；移除融合/重排/多样性选择精度 -22.6 pp——证据选择堆栈贡献巨大。
   - 边界阈值在 0.30-0.70 范围内精度波动仅 1.04 pp，说明系统对参数不敏感、稳健。
5. **核心结论**：长期记忆的精度-成本权衡**更多取决于整合粒度**而非仅保留信息内容；语义片段级整合是兼顾保真度与效率的可行路径。

## 7. 优点

- **问题定位精准**：系统诊断了"逐轮急切整合"这一被主流系统默认采纳却成本高昂的设计，提出了明确且可量化的替代方案。
- **方法设计优雅**：片段级批处理 + 语义边界检测，兼顾成本与保真度；类型化记录自包含化 + 跨片段消歧反馈，解决低级证据完整性问题。
- **端到端效率意识**：同时优化构建侧和查询侧；检索阶段仅一次 LLM 调用，其余全部为确定性操作，思路清晰。
- **实验说服力强**：两个差异明显的 benchmark（短对话密集 QA vs. 超长对话单查询）、两个骨干模型、多样基线、三阶段消融 + 参数敏感性分析，证据链条完整。
- **可复现性好**：提供了算法伪代码（Algorithm B.1、B.2）、详细实现参数（表10-14）、完整提示模板（附录F）和 token 记账规则。
- **公正的自我批评**：明确指出偏好类问题上弱于 MemoryOS，并坦诚局限（仅文本、未评估生产指标等）。

## 8. 不足与局限

- **偏好建模不足**：LongMemEval-S 偏好类问题 GPT-4.1-Mini 下 90.00%，低于 MemoryOS 的 100.00%；GPT-4o-Mini 下 70.00%，低于 MemOS 的 96.67%。专用 persona/用户档案模块可能有额外优势。
- **仅限文本模态**：未覆盖多模态记忆、多模态个性化场景。
- **未评估生产部署指标**：数据库延迟、embedding 索引存储增长、缓存行为、长期在线反馈、隐私治理、连续部署下的存储增长均未涉及。
- **未报告训练算力**：没有 GPU 型号、数量、训练时长等信息；由于全部使用托管 API，也算是一种资源依赖。
- **基线配置可能未完全优化**：未说明基线是否经过超参调优，基线可能未在其最佳状态下比较（不过这是多数论文的共同限制）。
- **构建记录保留策略**：当前实现不去重、不推断更新链接、不自动过期——保留全部历史证据虽有利于召回，但长期运行可能积累冗余。
- **开放性问题和偏差风险**：判断器（GPT-4o-Mini）与骨干模型出自同一模型家族，可能存在系统性偏好；LoCoMo 只用了 10 个对话，虽 QA 对密集但对话数较少，场景多样性有限。
- **查询上下文为计数型而非 token 预算型**：查询提示长度随所选证据文本变化，实际 token 消耗存在波动。
