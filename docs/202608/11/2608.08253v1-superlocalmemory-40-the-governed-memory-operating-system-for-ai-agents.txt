Abstract 

In plain terms. SuperLocalMemory is an open, local-first memory system for AI agents. It lets agents remember across sessions, machines, and people; it can run entirely on hardware you control, with no cloud provider in the memory path; and a team or a company can operate it without giving up isolation between one person’s context and another’s. What distinguishes it is less the feature list than the evidence standard applied to it: every reliability guarantee is stated as a falsifiable invariant, tested under an adversarial condition with a negative control, and reported together with an explicit account of what the experiment did not exercise. We call that practice AI Reliability Engineering , and this paper is an attempt to hold a memory system to it rather than to report capability numbers alone. The governance that makes those guarantees enforceable is cheap enough to leave on: 1 .687 ms at the median and 2 .728 ms at the 99th percentile per governed write ( n=1 ,000). The remainder of this abstract is technical. AI agents are moving from single-user assistants to shared infrastructure—teams, com-panies, and fleets of autonomous workers that must remember across sessions, machines, and people without leaking one context into another, and, for regulated or data-resident organizations, without a cloud provider in the memory path. The research and product landscape has answered this in fragments : memory SDKs and managed platforms, temporal context graphs, stateful agent runtimes with memory blocks, framework-native primitives, context APIs with connectors, and user-timeline stores. Each is strong on one axis. Few open, local-first runtimes unify retrieval quality, a learning brain, time-awareness, a knowledge graph, verifiable governance, and multi-tenant isolation in a single system an organization can actually operate. We present SuperLocalMemory 4.0 (SLM 4.0) , a governed, local-first memory operating system for AI agents: one control plane, organized as seven operating layers over six managed SQLite stores plus vector and graph projections, reachable through a CLI, an MCP server, an HTTP daemon, a dashboard, an editor plugin, and separately packaged adapters for nine agent frameworks, in three operating modes (fully local; local with an on-device model; provider-assisted). SLM 4.0 unifies, in one runtime: (i) multi-channel retrieval —dense semantic, BM25 lexical, temporal, Hopfield-associative, and spreading-activation candidates fused by reciprocal-rank fusion, over an information-geometric scoring and lifecycle substrate (Fisher-informed scoring, wired with a cosine-similarity fallback when per-memory variance is absent; sheaf-cohomology consistency and a Riemannian–Langevin

These capabilities become trustworthy under one governing design goal—one authenticated actor, one profile generation, one policy decision, one durable receipt, and one verifiable completion state. V4 enforces this invariant on the primary write path (the HTTP /remember route and internal ingestion admission), where the operation policy registry is evaluated and the generation fence applies; the other transports and operation kinds adopt the same gateway incrementally. We therefore present the invariant as the enforced design of the write path and the target architecture for the platform—not as a property already enforced on every surface. Four reliability mechanisms implement it: generation-fenced write admission, verifiable memory transactions (a transactional obligation ledger with per-projection apply/verify/compensate/erase owners covering the registered admission owners—bm25, temporal, vector—and a hash-checkable completion manifest), cross-store verified erasure over those three owners, and bi-temporal 

as_of demotion. A cross-surface operation policy registry in the governance control plane makes the same policy decision available to each participating surface. We evaluate the reliability spine by direct measurement against the candidate artifact: eleven fault-injection and mechanism scenarios, each repeated 200 times as a deterministic flakiness check; every repetition upheld its scoped component property (these repetitions are not independent Bernoulli trials and support no population failure-rate inference; fresh per-repetition SQLite databases are used for the database-backed experiments—two experiments are database-free and one uses synthetic projection-owner stand-ins; no single experiment exercises the full end-to-end path—transport, multi-process, mesh, and long-lived deployment fault-injection are future work); we report real-scale performance on a 1,232 MB memory-store copy (recall/write latency distributions, a concurrency sweep with zero writer-lock errors, and a 60-second resident-memory trace spanning 436.4–440.7 MB with no monotonic increase in that window—a definitive leak verdict needs a longer soak) together with a directly measured governed write-envelope overhead (1 .687 ms at p50 and 2 .728 ms at p99 over the ungoverned path, in-process); and we carry the published LoCoMo retrieval evidence from the V3 architecture (protocol-scoped, not a new V4 benchmark). Exact module and test counts are bound to the final release manifest rather than treated as architectural claims. We are explicit about scope: several capabilities exist individually in prior and commercial art—our contribution is their integration into one local-first, verifiable, governed runtime, together with the physical-store reliability layer and its measured results. The central systems contribution is a hash-verifiable projection-obligation and completion-manifest protocol across heterogeneous local stores under scoped admission; the admission invariant is enforced on

# 1 Introduction 

The last two years produced a rich literature on agent memory. Systems have advanced extraction and consolidation [1], temporal knowledge graphs [22], neurobiologically inspired retrieval [5, 6], OS-style hierarchical tiers [9, 18], memory as an OS-managed resource [12], multi-type and multi-agent coordination [25], efficient tiering with offline consolidation [3], strategic forgetting [27], and trust-gated retrieval [31]. Each improves one dimension of memory quality. 

From point solutions to a complete memory layer. A team standing up durable agent memory today still assembles it from specialized parts—each with its own trust boundary, failure model, and audit story. What we did not find, in a dated review of representative systems (Section 2), is a single runtime in which retrieval quality, a learning brain, time-awareness, a knowledge graph, verifiable transactions, and multi-tenant governance are the same system, running on infrastructure the organization controls. This paper contributes that runtime. 

Rent the LLM, own the memory. Foundation models are converging into an inter-changeable, rented capability; what an organization actually accumulates and must protect is its memory —the context, decisions, entities, skills, and provenance its agents build over time. That asset, and the governance over it, should be owned and operated by the organization on hardware it controls. A complete memory layer is therefore local-first by construction : storage, retrieval, the learning brain, governance, and optimization all run on the organization’s own infrastructure, with no provider required in the memory path (Modes A and B; Mode C is provider-assisted). 

The operating questions. A second class of questions becomes central the moment agent memory becomes shared organizational infrastructure: Can one client’s memory surface in another’s recall—on any retrieval path? When a user exercises the right to be forgotten, does the fact disappear from every registered projection store, with evidence? When agents on several laptops collaborate, can they share what they should without a cloud server? When an agent improves its own skills, can the organization bound and audit that self-modification? These are the operating conditions of team-scale, multi-surface agent memory. They are the province of AI Reliability Engineering —the systematic application of reliability, correctness, and governance principles to AI-augmented software—and SLM 4.0 is built for them. 

The governing invariant. SLM 4.0 ’s governing design goal is a single admission invariant— one authenticated actor, one profile generation, one policy decision, one durable operation receipt, and one verifiable completion state across the registered projection owners. V4 realises this invariant on the primary write path (the HTTP /remember route and internal ingestion admission), where the operation policy registry is evaluated and the generation fence applies; the other transports (MCP, CLI, WebSocket) and operation kinds adopt the same gateway incrementally. We present the invariant as the enforced design of the write path and the target architecture for the platform—not as a property already enforced on every surface. 

Contributions. SLM 4.0 consolidates a line of work—trust and behavioral foundations [19], an information-geometric retrieval substrate [21], and a living-brain learning and lifecycle model [20]—into one production system. On those foundations, V4 contributes and measures 

the reliability spine: generation-fenced admission, verifiable memory transactions with a hash-checkable completion manifest, cross-store verified erasure, and a cross-surface operation policy registry. We organize related work by the capability each system most advances and locate SLM 4.0 ’s distinct contribution in each area. 

Extraction and retrieval quality. Mem0 [1, 17] pairs LLM-based extraction with consolidation and reports strong LoCoMo results; its 2026 revision adds cross-memory entity linking and temporal accuracy gains [16]. HippoRAG [5, 6] models hippocampal indexing with Personalized PageRank. Many retrieval-quality systems treat tenant isolation as application metadata rather than a write-time fenced invariant; in the corpus we reviewed, we did not find one that specifies per-operation transactional consistency across multiple heterogeneous derived stores. SLM 4.0 ’s hybrid retrieval applies established hybrid-retrieval principles; we do not claim retrieval-architecture novelty. 

Temporal and knowledge-graph memory. Graphiti/Zep [22, 30] maintains bi-temporal edge validity with automatic invalidation—temporal correctness at the storage level. SLM 4.0 

places time at the retrieval-fusion level: a dedicated temporal candidate channel, non-destructive demotion of superseded facts, and an Ebbinghaus-parameterized recency model applied per fact after RRF fusion. We do not claim end-to-end temporal accuracy superiority; Graphiti’s bi-temporal storage is established prior art, and recent extraction-level results [16] raise that bar. 

OS-inspired memory. MemGPT/Letta [10, 18], MemoryOS [9], and MemOS [12] apply the OS metaphor to hierarchical context tiers and MemCube scheduling. We reuse the OS metaphor but apply it to authorization, multi-store durability, and governance. We do not claim the OS framing itself as novel. 

Self-improvement and governed skill evolution. The memory literature addresses improvement at the level of memory content —profile personalization, note re-linking, and sleep-time consolidation. We are not aware of a prior system (in the corpus reviewed through 2026-08-03) that governs the mutation of live agent skill configurations under a staged screen → confirm → mutate blind-verify → persist pipeline with candidate prove-nance, budget controls, and hash-linked state-transition history. 

Multi-tenancy, governance, and local-first. Multi-tenant isolation, compliance con-trols, and local-first operation are well represented—Supermemory [23], Mem0 [17], and Zep/Graphiti [30] all provide strong posture on these axes individually. Governed multi-tenant shared memory is itself concurrent work: MemClaw [15] provides scoped retrieval, temporal supersession, and policy-governed propagation; a production governed-memory architecture has been described [24]. SLM 4.0 ’s contribution is the integration into a single local-first runtime: a scope algebra enforced by profile-scoped predicates across all retrieval channels, a write-time gen-eration fence, and erasure verified across the three registered projection owners—with isolation and projection erasure measured .

Concurrent transactional memory work. Two July-2026 preprints address transactional agent memory at distinct layers. MemTX [11] stages writes in snapshot-isolated belief transactions with cascading repair—correctness at the semantic/belief layer . MemTxn [2] defines a transaction boundary for source-supported updates with complete-state recovery—correctness at the logical-state layer . SLM 4.0 ’s transactions center on a distinct layer : physical-store projection consistency —were all registered projection owners updated and independently verified, under one hash-checkable completion manifest with an honest degraded state? These layers compose: SLM 4.0 ’s manifest could sit beneath a MemTX belief transaction. We claim no priority over this concurrent work. 

# 3 Platform at a Glance 

SLM 4.0 is one control plane organized as seven operating layers, exposing a full arsenal of capabilities over a single managed store set. This section gives one honest paragraph per 4capability and the cross-system capability coverage map. 

3.1 Seven Operating Layers 

L1. Admission. Identity resolution, scope enforcement, idempotency check, and raw-evidence durability. A canonical write is admitted only after the ActorContext is derived from server-side state and the generation fence confirms the idempotency key is not replayed from a superseded profile-binding epoch. 

L2. Queryable Core. An atomic SQLite transaction writes the canonical fact row, the opera-tion receipt, and the transactional obligation ledger entries for every required projection owner—all or none. 

L3. Enrichment. Fact extraction, entity resolution, scene construction, temporal provenance derivation, graph edge writing, and optional embedding (mode-dependent). 

L4. Memory Brain. Behavioral pattern accumulation, feedback and reward recording, consolidation, soft-prompt generation, and guarded skill-evolution workflows. 

L5. Multi-channel Retrieval. Five candidate producers followed by RRF fusion, optional reranking, and entity-graph score enhancement. 

L6. Context Safety. Policy evaluation, provenance attachment, redaction of recognized secrets, boundary-marker neutralization, and context budget enforcement. 

L7. Operations. Lifecycle management, hash-chained audit, exact-match cache and reversible compression, Mesh peer-coordination, backup/restore, and daemon health surfaces. 

3.2 Capability Inventory 

Multi-channel retrieval. Five parallel candidate producers—dense semantic (with Fisher-Rao re-scoring), BM25 lexical, temporal (bi-temporal validity filter), Hopfield-associative, and spreading-activation—feed a single-pass Weighted RRF step ( k = 15) with strategy-adaptive channel weights. An optional cross-encoder reranker runs post-fusion; the entity-graph channel scores the fused candidate set but does not generate independent candidates. Healthy channels participate; degraded channels are excluded with provenance recorded in the response. Fisher-Rao scoring is wired ( retrieval/semantic_channel.py , core/engine_wiring.py ). 

Information-geometric substrate. The semantic channel applies Fisher-Rao geodesic re-scoring when per-memory variance data is available, falling back to cosine similarity otherwise. Sheaf-cohomology consistency checks and the Riemannian–Langevin lifecycle model were intro-duced in prior work [20, 21]; the EbbinghausLangevinCoupling class is experimental and has no production caller in V4. 

Entity knowledge graph. An AST-based code knowledge graph (blast-radius analysis, community detection, execution-flow tracing, incremental indexing with git-hook and file-watcher updates) and an entity store with typed edges and traversal API run inside the managed store. The spreading-activation channel uses this graph to surface multi-hop associations. 

Bi-temporal time-awareness. Each fact carries a three-date bi-temporal model (referenced / observation / interval). The as_of parameter is threaded across all primary recall surfaces— Python recall engine, HTTP /recall , MCP tool, CLI –as-of —and drives a temporal validity filter: facts are demoted in ranking under half-open event-validity semantics and transaction-time supersession ( point-in-time demotion , not snapshot deletion). References are UTC-normalized. 5Learning and behavior brain. A zero-LLM behavioral pattern miner captures tool-sequence patterns, correction events, temporal clusters, and cross-project assertions, which a soft-prompt generator distills into a compact context prefix prepended during session-context and auto-recall assembly (ordinary recall() ranking is unchanged; initialization failure disables injection fail-soft). Feedback loops (thumbs-up/down, explicit reward signals), outcome recording, a LightGBM ensemble reranker, and a cognitive consolidation queue are all wired and active by default. 

Governed skill evolution. SLM 4.0 governs mutation of live agent skill configurations under a screen → confirm → mutate → blind-verify → persist pipeline with candidate provenance, per-cycle budget controls (30-min wall / 10 LLM calls / 3 cycles-per-day, fail-closed on exhaustion), and DB-enforced hash-linked status transitions. Scope : the default configuration stops at verified quarantine; an explicit auto_approve flag—a configuration gate, not human or RBAC approval— can atomically promote a verified skill into the live loader with rollback on failure. Faithful parent-version lineage and generation tracking are not yet reported. 

SLM-Mesh coordination. SLM-Mesh provides serverless, per-tenant-isolated coordination through a local SQLite broker: authenticated peer messages, shared key/value state, and advisory locks with TTL-based expiry and fencing tokens—available in all three operating modes (zero-cloud Mode A through cloud Mode C). Cross-machine state/lock synchronization (opt-in) extends this to LAN peers: leaderless, pull-based last-writer-wins state convergence under ( revision , node _id ) and advisory-lock view convergence under fencing-token order, with a durable retrying outbox, optional mDNS discovery, and TLS/pinning/HMAC-signed transport. 

Scope : not linearizable consensus, not quorum replication, not a CRDT database; ordinary storage writes do not invoke the fence primitive; cross-machine coverage is currently the default profile, validated on a two-node loopback. 

Unified context optimization. An exact-match cache with tagged invalidation and a reversible compression stage (byte-exact recovery of originals) are co-located in the memory control plane and exposed on three surfaces (proxy, MCP, and skill), with savings telemetry. 

Governance-native controls. A governance control plane runs locally and in-process (no network call): a server-derived immutable ActorContext ; an 18-kind declarative operation policy registry; role-based access (OWNER / ADMIN / MEMBER / VIEWER lattice); multi-scope tenant isolation (personal / shared / global) enforced at write time; GDPR export/erasure with tamper-evident receipts; a hash-chained audit trail; and a deployment-context EU AI Act checklist that abstains from legal classification without intended-use evidence. Details appear in Section 5. 

Operational recovery and remediation. Auto-reconciliation redrives failed projection obligations and dead-letters exhausted ingestions; a write-path stall watchdog fast-fails new writers (rather than freezing all tenants) when the single writer stalls; and an OWNER/ADMIN remediation surface—one-click on the dashboard, plus CLI ( slm ops ) and MCP—lists and resolves (retry / force-reconcile / cancel) stuck, dead-lettered, or degraded operations, with failure counts surfaced on /health . Detailed in Section 6.5.

# 5 Governance Control Plane 

The strategic premise of SLM 4.0 V4 is rent the LLM, own the memory . Governance is not retrofitted—it is the substrate on which canonical operations run. The controls in this section execute locally and in-process, without a network call. Memory processing is fully local in Modes A and B; the opt-in Mode C may send configured embedding, reranking, extraction, or answer payloads to a provider, while governance state and decisions remain local. 

Governing invariant (scope). V4 realises the full envelope (one authenticated actor, one profile generation, one policy decision, one durable receipt, one verifiable completion state) on the canonical HTTP /remember path and internal ingestion, over the three registered projection owners; declared MCP tools and selected CLI mutations additionally obtain a shared policy 

decision but do not yet share that operation envelope or receipt; direct legacy mutations and HOOK/ADAPTER surfaces remain incremental. We present it as the enforced design of the canonical write path and the target for the platform, not as a property already enforced on every surface. 

5.1 Server-Derived Actor Identity 

ActorContext (core/actor_context.py ) is a frozen dataclass that carries the complete, server-resolved identity for a single operation. Its fields are populated exclusively from server-authenticated state—session tokens, daemon descriptors, the profile runtime, and RBAC results— never from the request body . Key fields: principal_id (stable user or operator identifier, never a raw session token); roles (a FrozenSet drawn from the lat-tice OWNER ≥ ADMIN ≥ MEMBER ≥ VIEWER, plus SYSTEM and ANONYMOUS); 

session_token_hash (first 16 hex chars of the SHA-256 of the raw token, for audit attribution only; no raw session material is retained on any path); transport (HTTP / MCP / CLI / MESH / HOOK / INTERNAL / DASHBOARD / ADAPTER). 

5.2 Operation Policy Registry

5.3 Multi-Scope Isolation and Profile Generation Fence 

SLM 4.0 separates two orthogonal isolation axes: the profile (individual / team / company namespace) and the scope (personal , shared , or global ) within and across profiles. Every tenant-owned memory table carries a profile_id column as a partition key; cross-scope access is default-deny . A fact in personal scope is not visible to a request scoped to shared unless the writer granted it explicitly—enforced at write time (scope label committed with the fact) via profile-scoped predicates across all five retrieval channels. The generation fence rejects a stale, superseded-epoch admitted write on the canonical remember path; it is not the retrieval-channel isolation mechanism. Scope of isolation claim: authorization-layer control, not cryptographic multi-tenancy; a single OS user with direct disk access is outside the threat model.

5.5 Hash-Chained Audit Trail and EU AI Act Deployment Checklist 

AuditChain (compliance/audit.py ) is a tamper-evident hash-chain audit log in its own SQLite file ( audit_chain.db ), completely independent of the main store. # 6 Reliability Spine 

The governance layer answers who may act and on which scope . This section answers how we guarantee that the action succeeds consistently . Four mechanisms form the V4 reliability spine: generation-fenced admission, verifiable memory transactions, cross-store verified erasure, and bi-temporal as-of. SLM-Mesh provides the coordination layer. Together they realise the governing design goal on the write path. 

6.1 Generation-Fenced Admission 

A profile deleted and recreated with the same ID must not allow a cached context to write into the new profile’s data. The generation fence uses a process-local, threading.RLock -protected, TTL-bound map of (profile_id, idempotency_key) → (epoch, timestamp) in 

storage/generation_fence.py , with entries expiring after 300 seconds. At admission, record_admission_epoch stores the current profile generation for the idempotency key. If two concurrent admissions record different epochs for the same key, the fence sets the entry to _CONFLICT_EPOCH = -1 —a sentinel that can never equal a real generation (≥ 0)—so both requests are subsequently re-jected. When CanonicalRememberRuntime._handle_admission processes the write, it calls admitted_epoch() and compares against the runtime’s current generation; a mis-match raises ValueError("epoch is stale") , which the WriteCoordinator wraps as 

WriteCoordinatorError before any projection writer is called. The generation epoch is server-derived and cannot be supplied by a caller. Figure 7 shows the fence protocol. Scope : in-process, TTL-bounded, not SQLite-backed; not a revision CAS; does not survive process restart. The canonical HTTP /remember and internal-ingestion boundaries synthesize a non-empty idempotency key (a UUID) when the caller omits one, so omission at those public boundaries does not bypass the fence.

6.5 Operational Recovery and Admin Remediation 

A shared deployment must ensure that a stuck or failed operation for one tenant neither corrupts nor silently blocks the others, and that every failure is either auto-recovered or resolvable by an operator. V4 layers three mechanisms on the transaction spine. 

Auto-recovery. The maintenance reconciler redrives pending and failed projection obli-gations (capped at ten attempts per obligation); the ingestion path retries a materialization up to ten times and then records the operation in a durable dead_letter_operations table with its content, error, and attempt count. Transient failures heal without human action, and a permanently failed operation is retained rather than lost. 

Stall isolation (write-path watchdog). The single-writer WriteCoordinator serializes 20 canonical writes for correctness. To keep one pathological operation from freezing every tenant’s writes, each in-flight item is watched: if the worker exceeds a stall threshold (default 30 s, far above the 1 s per-item deadline) on a single item, the coordinator trips a circuit breaker so that new submissions fail fast with an explanatory WriterStalledError (“write subsystem stalled; admin remediation required”) instead of queuing behind a dead worker; the breaker clears automatically once the item completes. Callers receive an immediate, actionable error rather than a silent hang. Scope : the watchdog surfaces and fast-fails a stall but does not forcibly terminate the worker thread—a hung native handler still requires a restart (future work). 

Surfacing and one-click remediation. Failures are made visible rather than buried in logs: the daemon /health and get_status surfaces report dead_letter_count ,

degraded_operations , and writer_stalled . An OWNER/ADMIN operator can enumer-ate and resolve them through one remediation surface exposed uniformly on the dash-board, the CLI ( slm ops list / slm ops resolve ), and MCP ( list_failed_operations ,

resolve_operation ), gated by the OPS_INSPECT /OPS_RESOLVE policy kinds with a full audit record on resolve. resolve supports three actions on a specific operation— retry (re-enqueue a dead-lettered ingestion), force-reconcile (redrive its projection obligations immediately, bypassing the periodic throttle), and cancel (mark it terminally handled). Because a large share of SLM 4.0 

operators are non-technical, the dashboard presents this in plain language—a health banner and a “needs attention” table with per-row Retry / Re-sync / Cancel buttons—so recovery requires neither the CLI nor raw SQL. These paths are covered by dedicated tests (stall-watchdog fast-fail and recovery, RBAC-gated listing, and resolve semantics).

10.2 Real-Scale Performance 

Performance was measured against a retained memory-store database copy (1,232 MB; 768-d embeddings), driving the real engine with warm caches, GC disabled during timed loops, and embedder warm-up excluded from timing. Provider scope : these figures use the in-process 26 sentence-transformers embedder ( nomic-ai/nomic-embed-text-v1.5 ), whose cold model load is 10,009.9 ms and is excluded; an earlier measurement of this suite against a warm Ollama endpoint recorded a 541.8 ms warm-up. Embedding provider and database size both materially affect these numbers, so both are stated rather than left implicit; figures produced under different providers are not directly comparable. 

Concurrency. Figure 12 sweeps 1–16 GIL-shared threads alternating store_fast writes and direct recall (the legacy bypass path, not the governed write path). Throughput rises from 0.9 to 18.4 ops/s across 1–16 workers, while median per-operation latency degrades from 74.9 ms to 1,009.4 ms as GIL and write-lock contention grow, with zero “database is locked” errors observed at any level under the single-writer, WAL-journaled design; we report the observation without attributing multi-process or transport causality. 

Latency. Figure 13 reports percentiles over n=300 warm operations on the 1,232 MB store. Recall is embedding-bound: 1.93 s at the median and 4.38 s at p99 with the in-process sentence-transformers provider. The 42.0 ms median for the legacy direct store_fast write path on that store bypasses canonical admission, the policy registry, the encrypted journal, projection obligations, and the completion manifest, so it does not bound governed-path cost. 

Governed write-envelope overhead. To bound the control-plane cost directly, we measured the canonical governed write envelope in-process (CanonicalRememberRuntime.remember() —the same path the HTTP handler calls af-ter request parsing: encrypted admission-journal prepare/dispatch/commit, the single-writer 

WriteCoordinator , the canonical SQLite write, and the projection obligation-ledger insert) against the ungoverned in-process write on a fresh store, n=1 ,000 warm calls each after a 30-call warm-up burst. The governed envelope runs at p50/p95/p99 = 3 .522 /4.427 /5.297 ms versus 1.835 /2.379 /2.569 ms ungoverned—a control-plane overhead of 1 .687 ms (p50) to 2 .728 ms (p99). 

Scope : in-process (HTTP transport and request parsing excluded; loopback HTTP typically adds 0 .5–2 ms); databases on a temporary filesystem, so persistent-disk fsync on the first journal write may raise p50 toward the low tens of milliseconds—these are floor numbers—and the ungoverned baseline is IngestionCommand.submit() , making the stated delta a conservative lower bound. A full end-to-end HTTP benchmark under multi-agent concurrency remains future work. 

Memory stability. Figure 14 tracks RSS across 60 s of sustained load. After initial warm-up, RSS remains within 436.4–440.7 MB with no monotonic upward trend (4 MB rounded spread; final 438.0 MB). # 11 Limitations and Threats to Validity 

Authorization-layer isolation only. Tenant and scope isolation are enforced by the autho-rization layer; a single OS user with direct filesystem access to the SQLite stores is outside the threat model. 

Mesh validated only at small scale. Per-device revocation and key rotation, WAN-latency and network-partition fault injection, and multi-machine operation beyond a two-node loopback remain future work. Mesh is coordination—not consensus, quorum, or a CRDT database. 

Temporal accuracy not benchmarked end-to-end. We measure temporal mechanisms ;we do not report agent-task accuracy against an external benchmark. The cross-surface as_of 

demotion path is newly wired and not yet benchmarked. The EbbinghausLangevinCoupling 

class is experimental with no production caller. 

Reliability evaluation is component-level. The harness drives real production modules over fresh per-trial SQLite databases but does not exercise the HTTP/MCP/WebSocket server stack, inter-process communication, or production-scale concurrency. The sqlite-vec ANN index is not loadable in the harness environment; exp1’s vector erasure is scoped to the 

embedding_metadata SQL table. Retained result artifacts record package version and platform but not a source commit or wheel hash. 

External long-context benchmarks are future work. No new V4 LoCoMo run is reported; V3-architecture LoCoMo results are carried forward, protocol-scoped. An end-to-end V4 benchmark against LoCoMo and LongMemEval is preregistered. 

Single-node local-first scope. All reliability results are from single-machine deployments; multi-node mesh behavior and distributed consistency are not characterized. 

Concurrent and closely related prior art. MemTX and MemTxn [2, 11] on adjacent transaction layers; MemClaw / Governed Memory [15, 24] on governed multi-tenant shared memory; PROJECTMEM [14] on local-first event-sourced agent memory. SLM 4.0 ’s position is a distinct local-first composition, not priority over any of these.

# 12 Novelty and Contributions 

We state novelty with corpus-bounded language: “not found in the searched corpus” means not described in primary sources reviewed through 2026-08-03—a dated review, not a priority claim. Several capabilities SLM 4.0 provides—multi-tenant isolation, compliance controls, 29 temporal memory, local-first operation—exist individually in shipping systems. We claim (a) their integration into one governed, local-first, verifiable runtime under a governing admission invariant (enforced on the primary write path; target architecture for all surfaces), and (b) specific innovations the V2–V4 line of work contributes. 

C1 — Governed skill evolution (major). A blind-verified, budgeted pipeline under per-cycle budget controls with append-only, hash-linked status transitions to a quarantine store. Not found in the corpus for live agent skill mutation. Scope: default stops at quarantine; 

auto_approve flag (not human/RBAC) can activate; faithful parent-version lineage not yet reported. 

C2 — SLM-Mesh: serverless governed coordination (major). Serverless, per-tenant-isolated coordination through a local SQLite broker, with optional remote peer discovery and message proxying, across all three operating modes. Scope: leaderless LWW, opt-in, default-profile, two-node-loopback validated; not consensus/quorum/CRDT; WAN-scale and per-device revocation are future work. 

C3 — Governance-native memory with deployment-context assessment (co-lead). Ascoped governance control plane in a local-first runtime: immutable server-derived actor identity, pure kind-keyed policy registry, role-based access, write-time generation-fenced isolation with verified projection-store erasure, hash-chained audit, a non-authoritative EU AI Act checklist that abstains without intended-use context, and operable recovery (auto-reconciliation, a write-path stall watchdog, and an RBAC-gated dashboard/CLI/MCP remediation surface for stuck or degraded operations). Cross-tenant isolation (exp5), erasure completeness (exp1), generation-fenced admission (exp7), and policy evaluation (exp8) are measured . Scope: authorization-layer isolation, not legal certification. 

C4 — Verifiable memory transactions (co-lead). An atomic canonical commit with a transactional obligation ledger, per-projection apply/verify/compensate/erase owners under generation fencing, and a hash-checkable completion manifest (COMPLETE / DEGRADED / FAILED). Distinct from and composable with concurrent belief-level [11] and logical-state [2] transactions. Manifest correctness and real compensate() behavior are measured (exp2). 

C5 — Time-aware memory (major). A shipped temporal stack: three-date model, bi-temporal storage, dedicated temporal retrieval channel, non-destructive superseded-fact demotion, Ebbinghaus recency model, and cross-surface as_of recall. Three temporal behaviors measured directly. 

C6 — Information-geometric retrieval brain, productionized (major). Five candi-date producers fused by RRF, over Fisher-Rao scoring, sheaf-cohomology consistency, and a Riemannian–Langevin lifecycle, together with an entity knowledge graph and unified caching and compression. Contribution is productionizing and governing this brain inside a multi-tenant runtime. 

C7 — Direct reliability evaluation method (supporting). A bracketed, positive-controlled, fail-loud fault-injection harness measuring agent-memory durability, isolation, admis-sion, and temporal guarantees against the candidate package. 30 13 Future Work 

Memory scaling via quantization. SLM 4.0 ’s context-optimization layer combines exact-match caching with reversible lossless compression to reduce working-set pressure at the session boundary. As deployment stores grow to tens or hundreds of gigabytes—a realistic trajectory for long-lived enterprise agents—a near-lossless vector-quantization tier for the semantic-channel em-bedding store becomes necessary. Gao and Long [4] showed that a codebook-free, random-rotation 1-bit quantizer achieves a provably tight error bound and outperforms product quantization on ANN recall at near-zero indexing cost; Zandieh et al. [29] extended this line, combining a polar-coordinate preprocessing stage [7] with a 1-bit quantized Johnson–Lindenstrauss resid-ual corrector [28] to reach near-optimal distortion across bit-widths. The natural SLM 4.0 

extension is a pluggable, data-oblivious quantization tier in the optimize layer that compresses stored embeddings without changing the retrieval interface, with the existing lossless path as a strict-reversibility fallback. 

Graph engineering and knowledge-graph maturation. SLM 4.0 maintains an entity knowledge graph with spreading-activation retrieval, but graph construction currently relies on LLM-extracted entities without automatic temporal-edge invalidation or community-level organization. Graphiti [22] demonstrates one concrete realization—an episode/entity/community architecture where a contradiction sets an expired_at timestamp on the superseded edge rather than deleting it, and a label-propagation step groups entities into communities with maintained summaries. Integrating temporal-edge invalidation into SLM 4.0 ’s entity-graph channel and adding community summaries as an additional retrieval signal are well-scoped extensions that would strengthen multi-hop and cross-entity recall. 

Temporal memory: point-in-time reconstruction and calibration. SLM 4.0 ’s as_of 

path performs superseded-fact demotion at query time but does not reconstruct full system state at an arbitrary past instant—in particular it does not yet apply as_of to the backup store or the sqlite-vec ANN index. Extending temporal-validity filtering to the ANN index and the restore path would close that scope gap and make point-in-time audits complete; wiring the (currently unwired) Fisher–Langevin posterior coupling would make the Ebbinghaus decay adaptive rather than fixed-parameter; and an ablation against the temporal categories of LoCoMo [13] and LongMemEval [26] would quantify the accuracy contribution of bi-temporal demotion. 

End-to-end agent retrieval benchmark. The evaluation here measures structural cor-rectness at the component level; it is not a retrieval-accuracy benchmark. A dedicated V4 suite should run SLM 4.0 as a live recall server across the LongMemEval [26] abilities and the LoCoMo [13] categories, exercise multi-session write/recall cycles that trigger the generation fence and the completion manifest, and report retrieval degradation under fault injection. He et al. [8] further show that LoCoMo-saturating agents still fail when memorization and action are coupled across sessions, motivating an additional pass on interdependent multi-session workflows. 

SLM-Mesh at WAN scale and per-device revocation. Extending the mesh beyond a LAN raises three problems: consistency under arbitrary partition (a causal-consistency or explicit CRDT model to remain correct across disconnect/reconnect); per-device revocation (invalidating a decommissioned device’s state across peers without a central coordinator); and message-content scrubbing before transit (mesh state values pass a secrets filter, but mesh_send 

payloads are not yet scrubbed pre-transmission). Each is a scoped, engineering-grade extension with clear acceptance criteria. 31 Persistent generation fence and watchdog upgrade. Two operational gaps are docu-mented as out of scope for this release. The generation fence is enforced in process memory and does not survive a restart; persisting the fence epoch to the control store and rehydrating on startup is a self-contained fix. The write-path watchdog detects a stalled worker and fails new writes fast, but does not yet kill and replace the thread; a kill-and-replace path with restart backoff and alerting would harden unattended, long-running deployments. 

Machine-checked formal proofs. The Verified Design Invariants of Section 7 are established here by implementation trace and fault-injection measurement. Upgrading them to machine-checked proofs (e.g. in Lean 4 or TLA +) would lift the guarantee from empirically upheld at N =200 per trial to proven for all executions conforming to the protocol . The completion manifest’s complete /degraded /failed derivation is a natural first target: a small, bounded state space tractable for model checking. 

# 14 Conclusion 

Agent memory is becoming shared infrastructure, judged by properties that retrieval-accuracy benchmarks do not capture: isolation between tenants, verifiable correctness of canonical operations, governed self-improvement, coordination without a central server, first-class time, and operable governance. SLM 4.0 addresses a specific, under-served point in this space—a local-first runtime that co-locates multi-scope isolation, verifiable memory transactions, and governance controls under one admission path, without requiring a cloud service. The contribution is not any single mechanism—bi-temporal storage, knowledge-graph retrieval, and GDPR-aware erasure each have strong prior art—but their composition into one verifiable, governed, open-source runtime, together with a physical-store transaction spine and a measured reliability evaluation. The all-2,200-repetitions fault-injection result is deliberately narrow: it shows the spine services upheld eleven deterministic structural properties at the component level; it does not claim retrieval-accuracy superiority over commercial services, nor does it substitute for an end-to-end multi-agent benchmark. Within that honest scope, SLM 4.0 delivers what its architecture promises—tenants isolated by a write-time fence rather than a retrieval-time filter, every cross-store write either verifiably complete or recorded as a hash-checkable degraded 

manifest, and erasure proved complete for the three canonical projection stores—as one instance of AI Reliability Engineering for the memory layer. The open threads of Section 13—near-lossless quantization as stores scale, graph engineering, an end-to-end V4 retrieval benchmark, WAN-scale mesh, a persistent fence, and machine-checked proofs—are each bounded extensions. 

SLM 4.0 lays the control plane; the reliability and quality properties reported here are a lower bound on what a production deployment requires.

It installs and runs on a single machine in three modes—fully local (no provider in the memory path), local with an on-device model, and provider-assisted—with no Docker, external graph database, or API key required for the default local mode. The reliability evaluation harness of Section 10 and its per-experiment result records are released alongside this paper. Reproducibility is per-result :the harness re-runs the fault-injection experiments on Python 3.13, whereas the carried-forward performance and V3 LoCoMo figures depend on artifacts (a ∼1 GB store and external model calls) that are not fully hash-pinned—retained records note package version and platform but not a source commit or wheel hash. The exact audited 4.0 build is pinned at release. 32 This preprint is self-contained. A longer internal technical report—with extended assumptions, full proofs, per-layer implementation detail, and an exhaustive capability inventory—underlies this work; it is not part of this preprint’s artifact.
