## 摘要
现代语言模型与智能体日益需要持久化记忆，以处理完整代码库、长交互历史及异构企业记录。关键挑战在于：在仅向答案模型传递有界源证据的同时，保持数亿级token的可检索性。我们提出MegaMem，一种源解析的双视图检索系统，将语义访问与生成证据分离。使用原始查询和变换查询检索蒸馏记录与详细证据；每一条蒸馏命中在互惠秩融合、去重与交叉编码器重排序之前，都会解析为一个不可变的源ID；仅在固定预算内排名最高的详细证据支持生成。回答后的归因可识别哪些加载的源支持固定答案。我们在EnterpriseRAG-Bench上评估MegaMem，该基准包含超过50万份异构企业文档和约6.5亿个token。MegaMem将Overall分数从68.22提升至82.26，并达到86.50的Correctness分数。这些结果表明，MegaMem能在有界生成上下文下支持超大规模持久记忆，同时保持强答案准确性。通过将可搜索记忆规模与答案上下文大小分离，MegaMem为实现对从数亿到十亿级token记忆的准确检索提供了一条实用路径。我们的代码可在https://github.com/xfab-xinyuansong/MegaMem.git获取。

## Abstract
Modern language models and agents increasingly require persistent memory for complete codebases, long interaction histories, and heterogeneous enterprise records. The key challenge is to keep hundreds of millions of tokens searchable while passing only bounded source evidence to the answer model. We introduce MegaMem, a source-resolved dual-view retrieval system that separates semantic access from generation evidence. Distilled records and detailed evidence are searched with original and transformed queries; every distilled hit resolves to an immutable source ID before reciprocal-rank fusion, deduplication, and cross-encoder reranking; and only the highest-ranked detailed evidence within a fixed budget supports generation. Post-answer attribution then identifies which loaded sources support the fixed answer. We evaluate MegaMem on EnterpriseRAG-Bench, which contains more than 500,000 heterogeneous enterprise documents and approximately 650M tokens. MegaMem improves Overall from 68.22 to 82.26 and reaches 86.50 Correctness. These results show that MegaMem supports ultra-large persistent memory while preserving strong answer accuracy under a bounded generation context. By separating searchable memory scale from answer-context size, MegaMem provides a practical path toward accurate retrieval over memories ranging from hundreds of millions to one billion tokens. Our code is available at https://github.com/ xfab-xinyuansong/MegaMem.git.

## 1. 核心问题与整体含义

### 研究动机
- 现代语言模型和智能体在长交互、多步骤规划、工具调用和知识密集决策中越来越依赖**大上下文**，因此持久记忆（persistent memory）成为核心基础设施。
- 实际系统需要保存完整代码库、长交互历史和异构企业记录，规模可达**数亿至十亿级token**。
- 原生长上下文模型（如Gemini 1.5）虽可处理百万级token，但存在 **“Lost in the Middle"位置偏差、多文档干扰、性能随长度衰减**等问题；而直接检索的RAG系统在大语料上容易召回噪声、遗漏关键证据。

### 核心矛盾
- **持久上下文（persistent context）**：系统可以搜索的全部语料，希望它尽量大；
- **证据上下文（evidence context）**：每次生成实际传入答案模型的有界详细证据，希望它尽量小且固定。

这两个目标之间存在根本张力：语料越大，检索越难，但生成上下文却不应随之膨胀。


### 问题定义（形式化）
系统在固定预算B下检索证据集：

- E(q) ⊆ D，且 tok(E(q)) ≤ B ≪ T

其中D为持久语料（T个token），E(q)为单次回答的证据上下文。目标是在**不增长E(q)的情况下扩展D的规模**。


## 2. 方法论：MegaMem 系统

### 总体架构
MegaMem 将“语义访问”和“生成证据”两个职责分离到不同阶段，形成**三阶段流水线**：

1. **双视图记忆构建（Dual-View Memory Construction）**
2. **多路线检索与证据解析（Multi-Route Retrieval & Evidence Resolution）**
3. **有界生成与事后归因（Bounded Generation & Post-Answer Attribution）**

其中核心原则是：**压缩表示仅用于定位内容，生成只使用详细源证据**。


### 2.1 双视图记忆构建

- 文档先经归一化、按标题和段落边界切分为**section-aware证据块**，形成详细证据视图 X = {x₁, …, xₙ}。
- 对每个详细块xᵢ，用提取器（gpt-5.4-mini 或全量提取器 FullExtractor，额外使用 gpt-5.4）生成至多三条**类型化记忆**：

  mᵢⱼ = (τᵢⱼ, uᵢⱼ, vᵢⱼ, πᵢⱼ)，πᵢⱼ = i

- 记忆类型包括五类：**事实（fact）、程序（procedure）、定义（definition）、要求（requirement）、决策（decision）**。
- 所有记忆携带**不可变的源块ID（π）**，指向其派生的详细证据。
- 最终建立两个独立索引：
  - **详细索引（detailed index）**：存储原始详细块的嵌入；
  - **蒸馏索引（distilled index）**：存储类型化记忆的嵌入。

两个视图指向同一底层证据，而非形成独立证据池。


### 2.2 多路线检索与证据解析

- 对每个问题q，系统构造多条查询路线：原始查询、规范化改写、术语多样化扩展。
- 每条路线同时检索详细索引和蒸馏索引。
- **核心步骤：所有蒸馏命中必须解析回其详细源块**，然后才进入融合阶段：

  C(q) = ⋃_{r∈Q(q)} (Retr(r, I_d) ∪ π(Retr(r, I_m)))

- 使用**加权互惠秩融合（weighted RRF）**合并来自不同路线的排序（γ=60），原始与规范化路线权重更高：

  S_RRF(x|q) = Σ_{r∈L(q)} w_r · 1[x ∈ r] / (γ + rank_r(x))

- 融合后由**交叉编码器（cross-encoder）**重排序，按源身份去重，并在证据预算B内打包最高排名的详细块。


### 2.3 有界生成与事后归因

- 答案模型**只看到详细证据块**：

  a = A(q, E(q))

- 蒸馏记忆、未选中源全部不暴露给生成模型。
- 答案固定后，独立的**归因模块**筛选支持答案的已加载文档：

  Z = C(a, E(q))，Z ⊆ docs(E(q))

- 归因**只能删减、不能修改**已生成的答案，也不引入新证据。

**重要推论**：查询变换负责扩大召回，重排序决定生成证据，事后归因则优化最终报告源集——三者职责明确分离。

- **移除蒸馏**：−14.15%
- **移除重排序**：−4.97%
- **移除查询扩展**：−3.55%
- **移除归因**：0.00%（答案不变，但报告文档从2.31增至5.00，即归因删除53.8%源）

### 效率
- 选择性详细证据将答案输入减少约69%，Correctness仅损失1.5点；蒸馏-only证据则损失约67点Correctness——证实蒸馏记忆适合作检索键但不适合作生成证据。

### 迁移
- FinanceBench（Overall 81.05）与HotpotQA（86.37）表现良好；
- LoCoMo（42.34）和UltraDomain（17.73）明显下降——文档导向的双视图设计不充分支持对话式与跨域记忆。

### 公式化解释（附录I）
- 双视图召回增益来自：R_dual = P(A) + P(M ∩ G ∩ Aᶜ)，蒸馏路线补充详细路线遗漏的证据；
- 规模衰减主要由P(S_N)（充分证据被选中）随干扰项增加而下降驱动。


## 7. 优点

1. **清晰的问题解耦**：将“可搜索记忆规模”与“生成上下文大小”彻底分离，本质上打破了RAG中“检索多少就生成多少”的耦合，框架概念简洁有力。
2. **源解析机制设计精妙**：所有压缩记忆只作检索线索，强制解析回不可变源ID后再融合，防止蒸馏失真污染生成——这一约束在同类记忆增强系统中少见。
3. **归因位置正确**：事后归因只能删源不能改答案，严格遵循“生成后归因”原则，使引用集更精确但对答案零影响。
4. **实验设计严谨**：
   - 开发和验证集严格分离（100/400题）；
   - 金证据干预有效隔离检索与生成瓶颈；
   - 多种协议（消融、规模、效率、迁移、诊断）构成完整证据链。
5. **规模可达性好**：250M token在线检索仅约1秒，成本极低（单题约0.75美分），实用性较强。
6. **记忆类型设计符合企业知识特点**：事实/程序/定义/要求/决策五类覆盖企业文档的主要语义形态。


## 8. 不足与局限

### 实验方面的局限
- **单次运行**：绝大多数结果未报告多次运行的方差，统计显著性存疑。
- **部分结果依赖估算**：详细证据唯一打包数据来自保留轨迹而非完整重跑。
- **不同协议间不可直接比较**：各实验的问题集、记忆规模、提取器各不相同，绝对值的可解释性受限。
- **InvDocs指标落后**：MegaMem的InvDocs为0.760，虽优于中间变体，但显著劣于发布基准领先者的0.470，即**报告文档中无效/不支持比例较高**——这是归因模块尚未完全解决的问题。

### 方法本身的局限
- **文档导向的设计**：对对话式（LoCoMo）和跨域（UltraDomain）记忆迁移效果差，表明当前表示难以捕获时间依赖、跨会话证据和跨域干扰下的检索需求。
- **未扩展原生注意力窗口**：MegaMem扩大的是“可搜索”的上下文，不增加底层模型的原生上下文长度。
- **查询扩展与可答性矛盾**：无条件查询扩展提高可答问题性能，但将信息不可答的Correctness从100.0%降至68.8%，需要可答性门控（当前依赖oracle才可完全恢复）。

### 基准与泛化性局限
- 主要验证集中在单一企业基准（EnterpriseRAG-Bench），外部基准数量有限且结果分化；
- 仅基于OpenAI API闭源模型（gpt-5.4系列），开放性、可复现性和对开源模型的适用性未验证；
- 论文中未报告GPU型号与数量等自有算力信息，仅提供API调用成本。

### 潜在偏差风险
- **评估依赖LLM-as-judge**：Correctness、Completeness等指标由gpt-5.4打分，可能存在对同源模型的偏好偏差，且未报告与人类评判的一致性系数；
- **记忆提取误差向下传导**：蒸馏过程依赖LLM提取类型化记忆，若提取出错或丢失关键信息，检索阶段无法恢复，且论文未量化提取质量对端到端性能的影响；
- **基准问题集规模有限**：500个问题（开发100+验证400）难以覆盖企业RAG的长尾场景，且问题-文档对可能存在隐含的分布偏斜；
- **自建基准风险**：EnterpriseRAG-Bench由作者构建，缺少第三方独立验证，任务难度与真实部署的对应关系未充分论证。

## 9. 未来工作

- **可答性感知门控**：引入显式的可答性判断模块，在查询扩展前过滤不可答问题，避免Correctness从100%降至68.8%的副作用；
- **动态预算分配**：当前固定证据预算B，未来可根据问题复杂度、检索置信度自适应调整每个查询的证据上限；
- **多模态与时间感知记忆**：扩展至表格、图表、代码等多模态证据，并为时间敏感型记忆（对话/日志）引入时间戳和会话ID作为解析键；
- **开源模型验证**：将记忆提取、嵌入、重排序和生成替换为开源模型（如Llama、Qwen），检验方法的模型无关性；
- **内存层级化**：将最热记忆驻留内存、冷记忆存储于磁盘/远端，进一步降低延迟和成本；
- **基于强化学习的检索策略**：将检索-生成-归因全链路建模为可微系统，联合优化证据选择和答案生成。

## 10. 总结

MegaMem提出了一种源解析的双视图检索框架，通过蒸馏记忆与详细证据分离、强制源ID解析、有界生成和事后归因，成功将持久记忆的可搜索规模扩展到数亿token级别，同时将生成上下文限制在固定预算内。在EnterpriseRAG-Bench上，它以82.26的Overall分数大幅超越发布基准领先者（68.22），且250M token规模的在线检索延迟仅约1秒，展示了工程实用性与可扩展性。

该工作的核心价值在于概念上的解耦：**记忆规模不再受生成上下文限制**。蒸馏视图负责“找到可能相关的源”，详细视图负责“提供生成所需的证据”，二者通过不可变源ID紧密绑定，既保证了召回覆盖率，又防止了压缩信息污染答案。实验证明，这种设计的性能损失主要来自检索环节而非生成环节，为后续优化指明了方向。

然而，MegaMem仍存在明显边界：它对对话式记忆和时间敏感型数据的适应力较弱，InvDocs指标反映归因尚未完全剔除无效源，且所有实验基于闭源API，缺乏可复现性和模型泛化性验证。此外，单次运行、协议不一致等实验问题也削弱了统计说服力。总体而言，MegaMem是对大规模RAG架构的一次有价值的重新设计，为未来“无限记忆”的语言智能体提供了可落地的基线方案。
